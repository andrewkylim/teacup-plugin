# Make a Teacup app

Teacup (kiit.fyi) is a web operating system for individuals and teams. An app for it is a small web app that runs on its own address on backed.cc, in a locked window, and reaches Teacup only through the kit. It keeps its records in **collections** declared in its manifest, so it needs no server code: Teacup keeps them in the person's workspace, live across devices, logs every change with Undo in Activity, and gives Claude tools for each collection once the person switches the app on for the Assistant.

Read these first, and keep to them: https://kiit.fyi/developers/building/, https://kiit.fyi/developers/data/, https://kiit.fyi/developers/guidelines/ and the manifest reference at https://kiit.fyi/developers/manifest/.

**You may check and upload the app. You never install it or grant it anything.** Uploading uses a developer key that can do nothing else; installing is where the person chooses what the app may reach, and only they do it, in Teacup's Apps. Never sign in to Teacup for them, never drive Teacup in a browser to install, and never print or copy their key.

Keep it small: one screen that does one job well beats three that half work. If the request needs something collections can't do (live typing together, server code, a secret key, sending email), stop and say so: those aren't available to apps yet.

## The steps

1. **Say what it is in one sentence**: who it's for and what changes for them. Decide what one record is ("a priced test: its name, its cap, what it's cost so far, and its stop date") and name the collection (`tests`). Choose a folder name (lower-case words joined by hyphens) and a name of 24 characters at most.
2. **Start it**: `npx teacup-os new <folder>` copies Teacup's template (React, the kit wired in, a working list of records) into a new folder.
3. **The manifest** (`app.json`): a one-sentence `description` (10 to 140 characters); each collection in `data.collections` with a plain description of one record and its `fields` (each a type, string, number or boolean, and a description with its unit or format: "The cap in pounds", "The day it stops, as YYYY-MM-DD"), which is what Claude's tools show and what the server holds saves to; give each record a `title` or `name` field so Activity can name it; `accepts` if other apps should be able to hand it text or links; `hosts` empty unless it truly contacts another site. Leave `permissions` empty unless it needs another app's records, and then only `<app>:read` or `<app>:write` on one of Teacup's ordinary apps, with a `reason`. Teacup sets the app's id, address, level and placement when it's uploaded.
4. **The icon** (`icon.svg`): one [Lucide](https://lucide.dev/icons/) glyph that says what the app does, as Lucide draws it (`viewBox="0 0 24 24"`, outlines, `stroke-width="2"`), its stroke white or a dark shade of the tile, on an `iconBackground` of its own (a hex colour or a gradient of them). No words, pictures, scripts or links; under 4,000 bytes. Never a letter in a box. Teacup draws the tile and sizes the glyph (the guidelines' "Your icon").
5. **The screen** (`src/App.tsx`, `src/app.css`): build it from the template's pattern and the kit's building blocks in `@teacup/kit/react` (https://kiit.fyi/developers/kit/ lists each with its rules and an example): `Page` for every screen (it keeps the room for Teacup's Home pill), `List` and `Row` (with `actions` for swipe, hold and ⋯), `Button`, `Field` and `Form` with `useForm`, `Sheet`, `Menu`, `Switch`, `SearchField`, `Empty`, `ErrorNote` for anything that went wrong (never an error's own message), `useToast` with Undo after a change, `useConfirm` instead of the browser's confirm, and `Icon` for Lucide glyphs. `useCollection<T>("<name>")` gives `records` (newest change first), `loaded`, `status`, `error`, `save(fields, id?)` and `remove(id)`; saves show at once. Use the kit's tokens for colour (or `light-dark()` pairs; one accent of the app's own at most), so light and dark both work, and its sizes for text, so it follows the text size. Show nothing until `loaded`, then the records or `Empty` with the one thing to do. Say nothing about saving until there's been a change, then a plain status (`aria-live`). Save when someone has finished (on submit, or when they leave a field), never on every key. Keep any running total as records of its own, since saves settle field by field and the last one wins. Nothing that only works on hover. Keep every file under 400 lines. Use the kit's verbs only (`act`, `useCollection`, `share`, `notify`, `badge`, `navigated`): nothing may touch `window.parent` or `window.top`. Copy: plain British English, no em dashes, "your workspace", never a person's name, never a raw error.
6. **Check it**: `npx teacup-os check` in the folder. It checks the manifest as Teacup will when it's uploaded, the page, the kit as the only door, the hosts, text boxes and the screen's height, and warns about anything the kit's rules would change (the browser's confirm, other icon libraries, fixed colours, text sizes that don't follow Teacup's, raw errors). Fix and check again until it passes with no warnings.
7. **Look at it on its own**: `npx teacup-os build` checks and builds it into `dist/` without uploading, and says how much JavaScript it ships against its `budgetKb` (set the budget from that, with a little room). Serve `dist/` on this computer (`python3 -m http.server <port> --bind 127.0.0.1` from inside it) and look at it at phone size (375 wide) and on a laptop. Outside Teacup it can't reach records, so expect a status saying so; check the layout, the empty state, tap targets and the console.
8. **An independent review**: start a fresh agent (never a fork) with only the app's folder and this brief: "You're reviewing a Teacup app against Teacup's guidelines at https://kiit.fyi/developers/guidelines/. It runs on backed.cc in a locked window and reaches Teacup only through its kit. Read the manifest and the code, go through every rule one by one (meets, doesn't meet with the file and line, or can't tell), and try to make it break them. Don't edit files. Return the findings ranked, most serious first." Fix everything it finds that's the app's, and check again.
9. **Upload it**: `npx teacup-os deploy`. If this computer isn't signed in, run `npx teacup-os login` first and tell the person: it shows a code and opens Teacup, where they check the code matches and approve it for their workspace (only an owner can). The first upload writes the app's Teacup id into `app.json`, so later versions update the same app; each later version needs a higher `version`. If the upload is refused, it says why in the same words Teacup shows: fix it and deploy again.
10. **Hand it over**: tell the person, in a few lines, what the app does, that it's uploaded and waiting in Teacup's **Apps**, under Ready to install, where they choose what it may reach and install it, what Claude will be able to do with it once they switch it on for the Assistant (its collection's tools), and anything the review raised that needs them. To upload new versions from GitHub on each release, offer to add `templates/teacup.yml` from this plugin as `.github/workflows/teacup.yml`.
