# Connect a website to Teacup

Teacup (kiit.fyi) is a web operating system for individuals and teams. A **website app** is a site that already runs on its own address, shown by Teacup in a locked window on a laptop and full screen on a phone. Teacup keeps only its `app.json` and icon; the site keeps its own servers, sign-in and database. Read https://kiit.fyi/developers/websites/index.md (the page as Markdown) first, and keep to it.

**You never change the project without the developer approving each edit.** Propose every change as its own edit, say why in a sentence, and let Claude Code ask them. Never batch edits, never switch on auto-accept, never deploy their site for them, and never touch files the change doesn't need. You may register the app (it only uploads `app.json` and an icon with their developer key); installing it, and switching on its device features, stay with an owner of the workspace, in Teacup's Apps. Never print or copy their key.

## The steps

1. **Check the live site**, from the project folder: `npx teacup-os connect <url>`. It reports, with ✓, ✗ and !: whether Teacup may frame it, cookies and storage inside a window, device features, what a window can't do, and a viewport. Then the header lines to change in this project, and an `app.json` to save. It changes nothing. If the address redirects elsewhere, use the address it ends at. If the site has an app behind a landing page (`/app`, say), connect the app's address.
2. **Explain the report** to the developer in plain words: what must change for it to open at all (the ✗s), and what's worth knowing (the !s).
3. **Propose the header change** as one edit in the file the report names (`_headers`, `vercel.json`, a Worker's code): set `frame-ancestors 'self' https://kiit.fyi` in the existing Content-Security-Policy (keep every other directive as it is) and remove `X-Frame-Options`. If the project has a copy of that file elsewhere (a release folder, say), say so and propose the same edit there. Nothing else in the policy changes.
4. **Propose `app.json`** as a new file, from the report's: a name of 24 characters at most, one sentence of description, `website` exactly as the site's address, `iconBackground` from its colours, a `window` that suits it (440 by 820 for a phone-first app), and for each device in `devices` a reason in the developer's words (ask them if it isn't obvious; never leave "Say why it needs this"). `permissions` and `hosts` stay empty: website apps can't reach Teacup's data yet.
5. **Offer an icon**: an `icon.svg` drawn only with shapes (no scripts, links, pictures or text), or none (Teacup shows the name's first letter).
6. **Offer, never insist on, the rest**, each as its own edit:
   - Where the report says links open new tabs or windows, or uses `alert`/`confirm`: what each would take, and that it's their call.
   - Loading the kit, so links go through Teacup's link sheet and the site can follow Teacup's light and dark and sign in with Teacup. A site with no build step vendors one versioned file (https://kiit.fyi/developers/websites/#using-the-kit-on-a-website-without-a-build-step): download `https://kiit.fyi/kit/teacup-<version>.js` for the newest version in `https://kiit.fyi/kit/versions.json`, check its SHA-384 against that list (`openssl dgst -sha384 -binary <file> | openssl base64 -A`) and tell them both, then propose it as a new file in their site's folder for vendored code. Never edit it, and never import from a "latest" address. An existing site connects with `connect({ name }, { theme: false })`, so the kit leaves its own styles alone.
   - Where the report says its sign-in is kept in the browser or on another site: Sign in with Teacup (https://kiit.fyi/developers/websites/#signing-in). It's a bigger change: describe it and leave it for a session of its own unless they ask.
   - Where the site has a `backend` and the report says it asks to send notifications itself: notifications through Teacup (https://kiit.fyi/developers/notifications/). Suggest a kind in `app.json` for each sort it sends from its server (`"to": "you"`, `"server": true`, a `purpose` of `"service"` for what the person set up or asked for, which starts ticked, or `"updates"` for news and tips, which starts unticked, a plain label and description, at most 8; never marketing labelled as a service), a key from `npx teacup-os notify-key <app id>` kept in the server's secrets, sending to people who signed in with Teacup through Teacup instead of its own push, and hiding its own notifications switch inside Teacup. Describe it; build it only if they ask, in a session of its own.
   - Where the site has a `backend` that keeps people's own data (a plan, a list, a log): tools for the Assistant and Claude (https://kiit.fyi/developers/websites/#offer-tools-to-the-assistant-and-claude). Its server answers MCP at an address it names in `backend.mcp`, checks Teacup's call token on every request, and lists a few tools in `backend.tools`, each with a `tier` (`read`, `write` or `outward`) and a plain `title`; it needs Sign in with Teacup first. Suggest two or three tools from what people would ask about their own data, with arguments kept small (no free text where a choice or a date will do). Describe it; build it only if they ask, in a session of its own.
7. **Deploying the site is theirs.** Once they say the header is live, check again with `npx teacup-os connect <url>`: Teacup may frame it should now be ✓. When `app.json` has `backend.mcp`, the report also lists its tools: with this computer signed in and the app's Teacup id in `app.json`, Teacup reads its server's list exactly as an upload will and says, tool by tool, what it would offer or why it can't (a ✗ stops the upload); without them, it only checks that the server turns away a call with no token, since only Teacup can sign one. A new app gets its id by registering once without `backend.mcp` and `backend.tools`; its server's `azp` check needs that id before its tools can be read.
8. **Register it** when they say so: `npx teacup-os connect <url> --register` from the folder with `app.json`. If this computer isn't signed in, run `npx teacup-os login` first and tell them: it shows a code and opens Teacup, where an owner checks the code matches and approves it. The first upload writes the app's Teacup id into `app.json`: tell them to commit it.
9. **Hand it over**, in a few lines: what changed in their project, that the app is waiting in Teacup's **Apps**, where an owner installs it and switches on its device features, and anything from the report still to do.
